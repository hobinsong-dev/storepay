# storepay

클라우드 POS 결제 백엔드 API.

가맹점이 여러 매장을 운영하고, 각 매장의 POS 단말이 주문을 만들고 결제하는 구조를 다룹니다.
결제사(PG) 역할을 하는 모의 서버를 함께 띄워, 외부 연동과 웹훅 수신까지 실제 HTTP 로 돌려볼 수 있습니다.
"동작하는 CRUD"보다 **결제 도메인에서 실제로 문제가 되는 지점들**(금액 신뢰, 동시성, 외부 PG 연동의 불확실성)을
어떻게 설계로 막았는지를 보여주는 데 목적이 있습니다.

## 기술 스택

| 영역 | 사용 기술 |
|---|---|
| 언어 / 런타임 | Java 17 |
| 프레임워크 | Spring Boot 3.5, Spring Data JPA |
| 쿼리 | QueryDSL 5.1 (동적 조건 검색) |
| 데이터베이스 | PostgreSQL 16, Flyway (스키마 버전 관리) |
| 문서화 | springdoc-openapi (Swagger UI) |
| 테스트 | JUnit 5, AssertJ, Testcontainers |
| 운영 | Spring Actuator, Docker multi-stage build (jlink), GitHub Actions |

## 구성

```
┌──────────────┐   승인/취소 요청    ┌───────────────┐
│ storepay-api │ ──────────────────▶ │ storepay-     │
│   :8080      │ ◀────────────────── │   mock-pg     │
│              │   서명된 웹훅       │   :8090       │
│              │ ──────────────────▶ │               │
└──────┬───────┘   일별 거래내역     └───────────────┘
       │                               (대사용 원장)
       ▼
  ┌──────────┐
  │PostgreSQL│
  │  :5432   │
  └──────────┘
```

`storepay-mock-pg` 는 결제사 역할을 하는 별도 모듈입니다.
승인·취소 응답을 주고, 비동기로 HMAC 서명된 웹훅을 되쏩니다.
승인 지연(`PG_APPROVE_LATENCY`)을 조절해 타임아웃 동작도 재현할 수 있습니다.
자체 원장을 들고 있어 일별 거래내역(`GET /v1/settlements?date=`)도 내려줍니다 — 대사의 상대편 장부입니다.

## 실행

```bash
# PostgreSQL + API + 모의 결제사 한 번에
docker compose up --build

# 또는 DB만 띄우고 애플리케이션은 로컬 실행 (결제사는 시뮬레이션으로 동작)
docker compose up -d postgres
./gradlew :storepay-api:bootRun
```

- API 문서: http://localhost:8080/swagger-ui.html
- 헬스체크: http://localhost:8080/actuator/health
- 지표: http://localhost:8080/actuator/prometheus (`storepay_` 접두어)

모든 응답에 `X-Request-Id` 가 실려 옵니다. 그 값으로 로그를 찍으면 한 번의 결제가 지나간
전 구간이 한 줄씩 따라 나옵니다.

```bash
curl -s -D- -o /dev/null -X POST localhost:8080/api/v1/payments \
  -H 'Content-Type: application/json' -H "Idempotency-Key: $(uuidgen)" \
  -H 'X-Request-Id: pos-terminal-77' \
  -d '{"orderKey":"ord_...","method":"CARD"}' | grep -i x-request-id

docker logs storepay-api | grep pos-terminal-77
```

## 테스트

```bash
./gradlew test
```

도메인 단위 테스트는 Docker 없이 바로 돌아갑니다.
동시성 테스트는 스레드를 출발 래치 앞에 모았다가 한 번에 풀어, 경합 구간이 실제로 열리게 합니다
(`Concurrently`). 만들자마자 실행하면 먼저 만들어진 스레드가 먼저 끝나 경합이 일어나지 않습니다.

대사·정산 테스트는 `Clock` 과 결제사 거래내역 포트를 둘 다 갈아 끼웁니다. 시계를 고정하지 않으면
"끝난 영업일만 대사한다"는 규칙 때문에 방금 만든 결제를 영원히 대사할 수 없고,
거래내역을 통제하지 않으면 불일치 상황 자체를 만들 수 없습니다.
같은 이유로 `docker compose` 로 띄운 상태에서는 오늘 영업일을 대사할 수 없습니다 —
실제 운영에서 이 배치는 다음 날 새벽에 돕니다.
통합 테스트는 Testcontainers로 실제 PostgreSQL 16을 띄워 **Flyway 마이그레이션과 JPA 매핑이
서로 맞는지까지** 검증하며, Docker가 없는 환경에서는 실패 대신 건너뜁니다.

> colima를 쓴다면 소켓 경로를 알려줘야 Testcontainers가 Docker를 인식합니다.
> ```bash
> export DOCKER_HOST="unix://$HOME/.colima/default/docker.sock"
> export TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock
> ```

## 설계 메모

구현하면서 내린 판단들을 적어 둡니다. 코드만으로는 "왜 이렇게 했는지"가 안 보이는 것들입니다.

### 금액은 클라이언트를 믿지 않는다

주문 생성 API는 총액 필드를 **받지 않습니다**. 매장 상품 마스터의 단가를 서버가 다시 읽어서 계산합니다.
POS 단말은 물리적으로 가맹점 손에 있고, 요청을 조작해 1원 결제를 만드는 건 어렵지 않습니다.
`Order.place()`가 유일한 생성 경로이고 `totalAmount`에는 setter가 없습니다.

### 단가는 주문 시점에 스냅샷으로 고정한다

`order_item`에 `product_name`과 `unit_price`를 복사해 둡니다.
상품 마스터를 조인해 금액을 계산하면, 나중에 가격을 올렸을 때 **과거 주문의 금액과 영수증이 같이 바뀝니다**.
정산과 세금계산서가 걸린 영역이라 과거 데이터는 불변이어야 합니다.

### 주문에 낙관적 락을 건다

`@Version`을 둡니다. 한 매장에 POS 단말이 여러 대인 환경에서는
같은 주문에 대한 결제 승인과 취소가 실제로 동시에 들어옵니다.
비관적 락은 POS 트래픽 패턴에서 대기가 길어지므로, 충돌 빈도가 낮은 이 경우엔 낙관적 락이 맞습니다.

### 페이징과 fetch join을 분리한다

컬렉션을 fetch join 하면서 동시에 페이징하면 Hibernate가 전체를 메모리로 읽어 들입니다
(`HHH000104` 경고). `OrderQueryRepositoryImpl.search()`는
① 조건에 맞는 주문 ID 페이지를 먼저 뽑고 ② 그 ID로 항목을 fetch join 하는 2단계로 나눕니다.
쿼리는 두 번이지만 N+1도 없고 페이징도 정확합니다.
`PageableExecutionUtils`로 count 쿼리가 불필요한 경우엔 아예 날리지 않습니다.

### 결제 승인은 멱등키로 선점한 뒤에만 결제사를 부른다

POS 단말은 응답을 못 받으면 같은 요청을 다시 보내고, 손님이 결제 버튼을 두 번 누르기도 합니다.
막지 않으면 카드가 두 번 긁힙니다. 그래서 `Idempotency-Key` 헤더를 필수로 받고,
키를 선점한 뒤에만 승인을 겁니다. 같은 키로 다시 오면 처음 결과를 그대로 돌려주고,
같은 키에 다른 내용이 오면 409 로 거부합니다.

기록은 Redis 가 아니라 **DB** 에 둡니다. 중복 방지는 결제 레코드 생성과 같은 트랜잭션 경계에서
다뤄져야 하는데, 캐시에 두면 캐시만 날아갔을 때 중복 승인이 그대로 뚫립니다.
응답 속도보다 중복 결제를 막는 쪽이 중요합니다.

선점은 독립 트랜잭션이어야 합니다. 호출 측 트랜잭션에 묶이면
유니크 제약 위반이 전체를 rollback-only 로 만들어 "이미 처리된 요청입니다" 응답조차 못 주고,
선점이 커밋되지 않아 동시 요청이 그대로 통과합니다.
또 **조회를 먼저, 삽입을 마지막**에 둡니다 — 제약 위반이 난 세션은 그 뒤 어떤 조회도 안전하지 않습니다
(Hibernate 가 flush 시점에 `AssertionFailure` 를 던집니다).

마지막 방어선은 DB 제약입니다. `payment` 테이블의 `order_id` 에 UNIQUE 를 걸어,
애플리케이션 검사를 동시 요청 두 건이 모두 통과하더라도 이중 결제가 저장되지 않게 했습니다.

### 승인은 트랜잭션 세 개를 겹치지 않고 차례로 연다

처음에는 `approve()` 전체를 `@Transactional` 로 감싸고 그 안에서 선점만 `REQUIRES_NEW` 로 열었습니다.
단일 스레드 테스트는 전부 통과했습니다. **16스레드 동시 승인 테스트를 붙이자 10건이
`Could not open JPA EntityManager for transaction` 으로 죽었습니다.**

요청 하나가 커넥션을 두 개 잡기 때문입니다. 바깥 트랜잭션용으로 하나를 쥔 채
안쪽 `REQUIRES_NEW` 용으로 하나를 더 달라고 합니다. 동시 요청이 풀 크기(기본 10)를 넘으면
모든 스레드가 첫 번째 커넥션을 쥔 채 두 번째를 기다리며 풀이 교착됩니다.
풀 크기를 키우는 건 임계점을 미룰 뿐 해결이 아닙니다.

그래서 `approve()` 는 트랜잭션을 아예 열지 않고(`NOT_SUPPORTED`) 세 단계를 차례로 호출합니다.

```
선점(tx1)  →  결제 처리(tx2)  →  선점 완료(tx3)
```

어느 시점에도 커넥션은 하나입니다. 트랜잭션 단위인 `PaymentApprover` 는 **별도 빈**으로 뺐습니다.
같은 클래스 안에 두면 프록시를 타지 않아 트랜잭션이 분리되지 않습니다.

### 선점 경쟁에서 진 쪽이 이긴 쪽의 선점을 지우고 있었다

실패하면 선점을 풀어 재시도할 수 있게 해야 합니다. 그 `release()` 호출이
선점 자체를 포함한 `try` 블록 안에 있었습니다.

동시 요청 16건 중 1건이 선점에 성공하고 15건은 `IDEMPOTENCY_IN_PROGRESS` 로 떨어지는데,
그 15건이 전부 catch 로 들어가 **이긴 쪽의 선점 행을 지웠습니다.** 지워진 틈으로 다른 요청이
다시 선점해 같은 주문에 결제를 또 만들고, 이긴 쪽의 `complete()` 는 사라진 행을 찾지 못해
조용히 넘어갑니다. 그 키로 재시도하면 존재하지 않는 결제를 가리킵니다.

고치는 방법은 선점 호출을 `try` **바깥**으로 빼는 것입니다.
선점에 성공한 요청만 그 선점의 주인이고, 주인만 풀 수 있습니다.

이 결함은 단일 스레드 테스트로는 영원히 드러나지 않습니다. 실제로 첫 동시성 테스트에서
결제가 **0건** 생성되는 것으로 나타났습니다 — 16건이 모두 실패한 것입니다.

### 결제사 재시도는 타임아웃에만 건다

4xx 는 결제사가 요청을 보고 거절한 것이라 다시 보내도 같은 답이 옵니다.
5xx 는 더 위험합니다 — 승인은 이미 처리됐는데 응답만 못 받았을 수 있어, 재시도하면 이중 결제가 됩니다.
그래서 재시도는 **연결 실패와 타임아웃에만** 겁니다.
읽기 타임아웃도 짧게 잡지 않습니다. 끊어도 결제사 쪽에는 승인이 남아 미결 거래가 생기고,
그 복구 비용이 기다리는 비용보다 큽니다.

### 승인 실패는 예외로 날리지 않는다

PG 가 거절하면 결제 건을 `FAILED` 로 **남깁니다**. 예외를 던져 롤백하면 실패 사유가 사라져
고객 문의에 답할 수 없습니다. 주문은 `CREATED` 로 남아 다시 결제할 수 있습니다.

### 웹훅은 받은 바이트 그대로 검증한다

웹훅 엔드포인트는 인증 없이 외부에 열려 있습니다. 서명을 검증하지 않으면 누구나
"결제가 승인됐다"는 요청을 보내 상품을 가져갈 수 있습니다.

본문을 DTO 로 역직렬화한 뒤 다시 직렬화해서 서명을 계산하면 필드 순서나 공백이 달라져 서명이 깨집니다.
그래서 컨트롤러가 `String` 으로 원문을 받아 그대로 검증합니다.

서명 대상에는 **타임스탬프를 포함**시킵니다. 본문만 서명하면 가로챈 요청을 그대로 다시 보낼 수 있습니다.
수신 측은 허용 시간(기본 5분)을 벗어난 요청을 서명이 맞아도 버립니다.
비교는 `MessageDigest.isEqual` 로 합니다 — 일반 `equals` 는 다른 바이트가 나오는 즉시 반환해서,
응답 시간 차이로 올바른 서명을 한 바이트씩 알아낼 수 있습니다.

### 웹훅의 진짜 용도는 유실된 응답의 복구다

승인 요청은 결제사에 닿았는데 응답이 네트워크에서 사라지면,
우리 쪽 결제는 `READY` 로 남습니다. **돈은 빠져나갔는데 장부에는 미결제인 상태**입니다.
웹훅이 그 간극을 메웁니다 — `READY` 인 결제에 승인 웹훅이 오면 그 시점에 승인 처리합니다.
이미 동기 응답으로 처리된 건이면 아무것도 하지 않습니다.

결제사는 at-least-once 로 보내므로 같은 이벤트가 두 번 옵니다.
`webhook_event.event_id` 에 UNIQUE 를 걸어 두 번째부터는 무시합니다.
이 방어가 없으면 취소 웹훅이 두 번 들어와 환불이 두 번 일어날 수 있습니다.

### 대사는 고치지 않고 찾아내기만 한다

우리 장부와 결제사 장부를 영업일 단위로 맞대어 보고, 어긋난 건을 네 가지로 나눠 기록합니다.

| 유형 | 뜻 | 원인 |
|---|---|---|
| `MISSING_IN_PG` | 우리는 승인인데 결제사에 없음 | 결제사 쪽에서 취소·실효 |
| `MISSING_IN_INTERNAL` | 결제사에는 있는데 우리에게 없음 | 승인 응답과 웹훅을 모두 유실 |
| `AMOUNT_MISMATCH` | 금액이 다름 | 부분취소 반영 시점 차이 또는 사고 |
| `STATUS_MISMATCH` | 상태가 다름 | 취소가 한쪽에만 반영 |

불일치를 찾아도 **결제 상태를 바꾸지 않습니다.** 어느 쪽이 옳은지는 결제사 원장과 매입사 통보를
함께 봐야 정해지는데, 배치가 멋대로 한쪽에 맞춰 버리면 틀린 쪽으로 맞춘 경우를 되돌릴 근거가 사라집니다.
양쪽 값을 **둘 다** 저장하는 것도 같은 이유입니다 — "다르다"만 적어두면 조사 시점에 당시 값을 다시 못 구합니다.

금액 비교는 `compareTo` 입니다. `equals` 로 비교하면 `10000` 과 `10000.00` 이 달라 매일 전 건이 불일치로 잡힙니다.

결제사를 못 부른 경우는 "불일치 0건"이 아니라 `FAILED` 로 남깁니다. 조회 실패를 성공으로 처리하면
불일치가 없는 것처럼 보여 그대로 정산이 나갑니다.

### 영업일 경계는 설정으로 뺀다

영업일을 자르는 타임존이 `storepay.settlement.zone` 입니다. 서버 기본 타임존을 쓰면
컨테이너 TZ 가 UTC 인 순간 경계가 9시간 밀려 KST 오전 9시 이전 거래가 전날 정산으로 넘어갑니다.

구간은 **반열린** `[00:00, 다음날 00:00)` 입니다. 양끝을 모두 포함하면 자정에 승인된 건이
어제와 오늘 정산에 두 번 잡혀 그만큼 돈이 두 번 나갑니다.

시각은 `Instant.now()` 가 아니라 주입받은 `Clock` 에서 가져옵니다. 직접 부르면
"영업일 경계에서 어떻게 동작하는가"를 테스트할 방법이 없는데, 정산은 날짜 경계가 곧 사업 규칙입니다.

### 수수료 반올림은 기본값이 없는 사업 결정이다

두 가지를 명시적으로 정했고, 둘 다 테스트로 고정했습니다.

**건별 계산 후 합산.** 999원 결제 세 건의 수수료는 건별로 22원씩 66원이지만,
합산(2,997원) 후 한 번에 계산하면 68원입니다. 결제사 청구서가 건별로 오므로
합산 후 계산하면 우리 장부와 청구서가 매일 몇 원씩 어긋납니다.

**원 단위 절사**(`RoundingMode.DOWN`). 수수료를 버리는 방향이라 가맹점에 유리합니다.
`HALF_UP` 으로 두면 반올림된 1원이 건수만큼 쌓여 분쟁이 됩니다.

취소하면 그 건의 수수료도 함께 돌려줍니다. 돌려주지 않으면 전액 취소된 거래에서
가맹점이 팔지도 않은 매출의 수수료만 부담합니다.

### 취소는 승인일이 아니라 취소일에 잡는다

어제 판 것을 오늘 취소하면 **오늘** 정산에서 차감합니다. 승인일로 되돌려 잡으면
이미 지급이 끝난 날짜의 정산을 다시 열어야 하는데, 지급은 되돌릴 수 없습니다.

대신 당일 지급액이 **음수**가 될 수 있습니다. 0 으로 깎지 않고 음수를 그대로 남겨
다음 지급에서 상계합니다 — 깎아 버리면 그만큼을 영원히 회수하지 못합니다.
그래서 `settlement.fee_amount` 에도 하한 제약을 두지 않았습니다.

### 대사는 덮어쓰고 정산은 덮어쓰지 않는다

같은 날짜를 다시 대사하면 이전 결과를 **대체**합니다. 결과가 여러 벌 남으면
"그날 불일치가 몇 건이냐"에 답이 두 개가 되고, 타이밍 차이로 생겼다가 재실행에서 사라진
불일치를 구분할 수 없습니다.

정산은 반대로 이미 마감된 날짜를 거부합니다. 뒤에 **지급**이라는 비가역 동작이 달려 있어서,
운영자가 같은 날짜를 두 번 돌리는 것만으로 돈이 두 번 나가면 안 됩니다.
다시 집계하려면 기존 정산을 명시적으로 취소해야 합니다.

정산은 대사가 끝나고 불일치가 0건인 영업일만 가능합니다. 배치도 불일치를 만나면
멈추고 사람을 기다립니다.

### 추적 키는 로그 패턴에 박고, 요청이 끝나면 통째로 비운다

모든 응답에 `X-Request-Id` 를 실어 보냅니다. 결제 장애 문의는 "몇 시쯤 결제가 안 됐어요"로
들어오는데, 그 시각대의 로그를 전부 뒤지는 것과 ID 하나로 찍는 것은 대응 시간이 자릿수로 다릅니다.
클라이언트가 보낸 값이 있으면 이어받아 POS → 중계 서버 → 결제 API 구간을 하나로 묶습니다.

다만 받은 값을 그대로 쓰지는 않습니다. 이 값은 로그 한 줄과 응답 헤더에 그대로 들어가므로,
개행이 섞이면 가짜 로그 줄을 심거나 응답 헤더를 쪼갤 수 있습니다. 영숫자와 `-_` 만, 64자 안에서
통과시키고 나머지는 새로 발급합니다.

추적 키는 코드가 아니라 **로그 패턴**에 박아 뒀습니다(`logging.pattern.console`).
매번 파라미터로 붙이는 방식은 빠뜨린 줄이 생기고, 하필 그 줄이 장애 때 필요한 줄이 됩니다.

```
2026-10-30T07:51:33.348Z  INFO [pos-terminal-77 pay_mvuo7w2h_vjeguvnig8] [http-nio-8080-exec-4] ...
                                └─ requestId ─┘ └──── paymentKey ─────┘
```

MDC 는 **스레드 로컬**입니다. 요청이 끝날 때 비우지 않으면, 처리 도중 깊은 곳에서 넣은 결제 키가
톰캣이 그 스레드를 재사용하는 **다음 요청의 로그에 찍힙니다.** 그래서 가장 바깥 필터가
`MDC.clear()` 로 통째로 비웁니다 — 키를 하나씩 지우는 방식은 새 키가 생길 때마다 빠뜨리게 됩니다.
스케줄러처럼 필터를 타지 않는 경로는 각자 `try/finally` 로 되돌립니다.

운영에서는 `LOG_FORMAT=ecs` 로 JSON 한 줄을 내보냅니다. 사람이 읽는 형식 그대로 수집기에 넣으면
`requestId` 로 검색할 수 없어, 추적 키를 붙여 둔 의미가 사라집니다.

### 지표는 집계용, 로그는 건별 추적용

메트릭 태그에 `paymentKey` 같은 값은 **절대 넣지 않습니다.** 태그 조합마다 시계열이 하나씩 생기므로,
건별로 유일한 값을 넣으면 거래 수만큼 시계열이 생겨 수집기가 먼저 죽습니다.
건별 추적은 로그(MDC)의 일이고, 메트릭은 집계의 일입니다. 테스트로 고정해 뒀습니다.

승인 결과는 세 갈래로 나눠 셉니다.

| outcome | 뜻 | 알림 |
|---|---|---|
| `approved` | 승인 성공 | — |
| `declined` | 결제사가 정상 응답으로 거절 (한도 초과 등) | 비율 급변 시에만 |
| `failed` | 우리 쪽 규칙이나 장애로 승인에 이르지 못함 (`error` 태그로 코드 구분) | 즉시 |

거절과 실패를 한 카운터에 담으면 한도 초과가 늘어난 것인지 장애인지 구분할 수 없고,
결국 아무도 그 알림을 보지 않게 됩니다.

결제사 호출은 `success` / `error` / **`timeout`** 을 나눠서 잽니다. 타임아웃은 "실패"가 아니라
**결과를 모르는 상태**라, 같은 실패로 묶으면 미결 거래가 늘고 있다는 신호를 놓칩니다.
빠르게 떨어지는 실패가 평균을 끌어내려 "응답시간은 정상"으로 보이는 것도 막습니다.

지연 히스토그램은 범위를 정해 둡니다(20ms~10s). 기본값은 1ms~30s 를 덮어
태그 조합마다 버킷이 70개 넘게 생기는데, 카디널리티를 걱정한다면서 히스토그램으로 되돌려 놓는 꼴입니다.

대사 불일치는 **유형별로** 셉니다. 합쳐 놓으면 "오늘 3건"만 남는데,
타이밍 차이로 생겼다 사라지는 `AMOUNT_MISMATCH` 3건과 손님 카드는 긁혔는데 우리 매출이 없는
`MISSING_IN_INTERNAL` 3건은 대응의 급박함이 전혀 다릅니다.

### 웹훅 재전송은 발신 측에 재시도가 있어야 성립한다

수신 측은 아직 모르는 결제의 웹훅에 일부러 409 를 줍니다. 그런데 모의 결제사에 재시도가 없었습니다.
컨테이너로 띄워 확인해 보니 **승인 트랜잭션이 커밋되기 전에 도착한 웹훅이 409 한 번으로 끝나고,
그 뒤로 아무도 그 결제를 복구해 주지 않았습니다.** 동기 응답이 살아 있어서 결제가 멀쩡해 보였을 뿐,
응답이 유실되는 진짜 상황에서는 복구 경로가 없는 상태였습니다.

"재전송을 유도한다"는 설계는 발신 측이 실제로 다시 보낼 때만 성립합니다.
모의 결제사에 지수 백오프 재전송을 넣고 나서야 끝까지 돌아갑니다.

```
승인 → 웹훅 전송 실패 (1/5) 409 → 200ms 대기 → 웹훅 전송 완료 (attempt=2)
```

재시도할 때 **이벤트 ID 는 바꾸지 않습니다.** 바꾸면 수신 측 중복 방지가 무력해져
재전송이 곧 중복 처리가 됩니다. 반대로 **서명은 매번 새로 만듭니다** —
타임스탬프가 서명 대상에 들어 있어서, 처음 만든 서명을 재사용하면
수신 측의 허용 시간 검사에 걸려 영영 통과하지 못합니다.

### 응답 DTO 는 트랜잭션 안에서 만든다

`open-in-view: false` 이므로 컨트롤러가 돌 때는 영속성 컨텍스트가 이미 닫혀 있습니다.
서비스가 엔티티를 반환하고 컨트롤러에서 DTO 로 매핑하면,
지연 로딩 필드에 닿는 순간 `LazyInitializationException` 이 납니다.

조회 API 라면 500 하나로 끝나지만 **쓰기 API 에서는 훨씬 나쁩니다.**
주문 취소를 예로 들면 트랜잭션은 이미 커밋돼 DB 상태는 `CANCELED` 인데
응답만 500 으로 나갑니다. 클라이언트는 실패로 알고 재시도하고, 서버는 이미 취소된 상태입니다.
결제 시스템에서 가장 피해야 할 종류의 불일치입니다.

그래서 응답 DTO 조립을 애플리케이션 레이어(`@Transactional` 안)로 내렸습니다.
엔티티는 레이어 밖으로 나가지 않습니다.
`OrderApiIntegrationTest` 는 `@Transactional` 없이 돌아갑니다 —
테스트에 트랜잭션을 걸면 세션이 열린 채라 이 버그를 못 잡기 때문입니다.

### 조건 검색은 Spring Data 프래그먼트가 아니라 포트로 붙였다

QueryDSL 조건 검색을 `OrderRepositoryImpl` 같은 Spring Data 커스텀 프래그먼트로 붙이면,
구현체가 **인터페이스와 같은 패키지에 있어야만** 탐색됩니다
(다른 패키지에 두면 `No property 'search' found for type 'Order'`로 기동이 실패합니다).
그 제약을 따르면 QueryDSL 코드가 도메인 패키지로 끌려 들어옵니다.

그래서 `OrderQueryRepository`를 도메인이 선언하는 포트로 두고,
QueryDSL 구현은 `infrastructure`에 어댑터로 뒀습니다. 의존 방향이 한쪽으로만 흐릅니다.

### 외부 식별자와 PK를 분리한다

API는 `ord_lz4k2x_8fh3jq91mv` 같은 키를 노출하고 bigint PK는 내보내지 않습니다.
순차 PK를 노출하면 하루 주문량이 그대로 추측되고 스크래핑 대상이 됩니다.
생성 시각(36진수) + 난수 조합이라 시간순 정렬은 유지되면서 값은 예측할 수 없습니다.

### 스키마는 Flyway만 바꾼다

`ddl-auto: validate`입니다. 엔티티와 실제 스키마가 어긋나면 **기동 단계에서 죽습니다**.
운영 중에 조용히 틀리는 것보다 낫습니다.
통합 테스트가 실제 PostgreSQL에 마이그레이션을 돌리므로, SQL 오류는 CI에서 잡힙니다.

### 실행 이미지는 jlink 로 줄였다

풀 JDK 를 그대로 실행 단계에 쓰면 576MB 입니다. 대부분이 런타임에 쓰지 않는 컴파일러와 도구입니다.
`jlink` 로 실제 필요한 모듈만 골라 런타임을 만들고 `alpine` 위에 얹어 **230MB** 로 줄였습니다.

베이스 이미지는 `amazoncorretto:17-alpine` 입니다.
`eclipse-temurin` 의 alpine 태그는 amd64 만 제공해서 Apple Silicon 에서 빌드가 깨집니다.

## 도메인 모델

```
Merchant (가맹점)  1 ── N  Store (매장)  1 ── N  Product (상품)
                                 │
                                 1
                                 │
                                 N
                              Order (주문)  1 ── N  OrderItem (주문 항목)
                                 │
                                 1
                                 │
                                 1
                             Payment (결제)  1 ── N  PaymentCancel (취소 이력)

ReconciliationRun (일별 대사)  1 ── N  ReconciliationMismatch (불일치)
Settlement (가맹점 일 정산)    ── N:1 ──  Merchant
```

상태 전이

```
Merchant : PENDING → ACTIVE → SUSPENDED → (ACTIVE 복귀 가능)
                            → TERMINATED (복귀 불가)

Order    : CREATED → PAID
              │        │
              └────────┴──→ CANCELED

Payment  : READY → APPROVED → PARTIAL_CANCELED → CANCELED
              │        │                             ↑
              │        └─────────────────────────────┘
              └──→ FAILED
```

`READY → APPROVED` 로 가는 경로는 두 개입니다. 결제사의 동기 응답, 그리고 응답이 유실됐을 때의 웹훅.
어느 쪽이 먼저 도착하든 결과는 같아야 합니다.
